## Included capability

M21 delivers only completed M20/SPEC-009:

- recursive static local presentation forests on direct nested-object and
  collection-item template owners;
- the existing section, tabs, accordion and bounded logical-grid family at
  every admitted owner, with owner-local direct-child membership;
- generic normalized presentation definitions that default to the existing
  root `FormNodeDefinition` domain;
- immutable template forests shared by concrete collection items, without
  item identity, index, value, baseline or runtime authority;
- deterministic compiler diagnostics and atomic default-forest fallback;
- independent Standard/DOM, native Angular and Angular Aria projection; and
- stable per-item UI state, qualified IDs, static-label reuse and mandatory
  native fallback without changing application-owned controlled state.

No snapshot, method, operation, scope, validation, persistence, submit or data-
authority contract changes. No new raw presentation entry kind, package entry
point, Angular provider or CSS property is added.

## Public migration from M19

The `0.4.0` core/base and `0.2.0` pilot source line is an incompatible Public
Experimental MINOR migration. Existing root-only authored source retains its
meaning, but manually authored normalized definitions and external Angular
container implementations must adopt the changes below.

### Core raw and normalized definitions

- `ObjectUiSchema.presentation` and `ItemUiSchema.presentation` are new
  optional authoring members. An object forest owns only that object's direct
  normalized children; an item forest owns only the direct editable children
  of its static item template.
- `ArrayUiSchema`, `FieldUiSchema`, primitive leaves and identity-property UI
  entries do not gain `presentation`. A collection remains atomic in its
  parent's forest and its `item.presentation` owns item descendants.
- `PresentationEntryDefinition`, `PresentedFormNodeDefinition`, section, tabs,
  accordion, panel, grid and grid-item definitions now accept a defaulted
  `FormNodeDefinition | FormNodeTemplate` generic domain.
- `TemplatePresentationEntryDefinition` is the only new named Public core
  export. Unparameterized `PresentationEntryDefinition` still wraps only
  `FormNodeDefinition`.
- `ObjectFieldDefinition.presentation` remains required and
  `ObjectNodeTemplate.presentation` plus
  `ObjectItemTemplateDefinition.presentation` become required immutable
  template forests. Manually authored objects/items must supply their default
  child-order forest.
- Section and advanced-presentation text definition domains widen to ordinary
  definitions or templates. `TextResolutionContext` widens only transitively;
  it gains no owner path, item identity, value, baseline or operation authority.
- Compiler diagnostics, fallback and manual-definition validation widen only
  for these local forests.

Example manual default forest:

```ts
const object: ObjectFieldDefinition = {
  // existing object members
  presentation: children.map((node) => ({ kind: 'form-node', node })),
};

const item: ObjectItemTemplateDefinition = {
  // existing item-template members
  presentation: children.map((node) => ({ kind: 'form-node', node })),
};
```

### Base Angular container SPI

The existing container definition, render model and tester now accept the
widened ordinary-or-template node domain. Entry and panel outlet inputs widen
in the same way. Renderer type, registration, provider and root exports remain
unchanged.

External renderers must narrow a wrapped node by `node.kind`; they must not
assume an absolute `path` exists. Testers still receive one exact deeply frozen
container and renderers receive only the deeply frozen render model. Neither
receives raw schemas, snapshots, item addresses, values, operations, resolver,
diagnostics or Internal owner context.

```ts
const tester: AngularPresentationContainerTester = (definition) =>
  definition.kind === 'tabs' ? 20 : null;
```

Native Angular projects every admitted local forest and preserves the existing
claim, cleanup and mandatory-fallback behavior.

### Angular Aria pilot

The pilot keeps the single
`provideSchemaEngineAngularAriaContainers()` root export, opt-in
`./styles.css`, four registrations and six Public Experimental CSS properties.
Its behavior widens to project local ordinary/template forests and concrete
item instances. It adds no Public contract or style.

## Installation and live-state model

### Reviewed local/candidate state

Until exact registry observation says otherwise, consumers must use the
verified M19 live line. M21 exact installs are not advertised as available and
`@next`, `latest` or an unqualified install must not be described as resolving
to M21.

After each package is separately published and verified, its exact version is
the safest installation form. `@next` may be recommended only for the package
whose observed alias resolves to the inspected M21 bytes. No coordinated
consumer evidence is accepted from a mixed `next` state.

The intended exact forms, unavailable until their publication is observed,
are:

```sh
npm install @rabassoft/schema-engine@0.4.0
npm install @rabassoft/schema-engine-angular@0.4.0
npm install @rabassoft/schema-engine-angular-aria@0.2.0
```

### Partial live state

Publication under `next` is dependency-first: core, base Angular, then pilot.
After core only, preserve exact core `0.4.0`; after base, preserve the exact
`0.4.0` pair without claiming coordinated completion; after pilot, preserve
exact `0.2.0` and reverify all three exact/`next` aliases before any default
transition.

The established `latest` transition is deepest-dependent-first: pilot, base
Angular, then core. Pilot-first and base-second states are planned mixed
windows and supply no coordinated `latest` or unqualified evidence. Every
write and every recovery mutation requires its own immediate approval and
post-write observation.

### Completed live state

Only observed exact bytes plus core/base `next/latest: 0.4.0`, pilot
`next/latest: 0.2.0`, and passing exact/`next`/`latest`/unqualified lower/latest
native and pilot consumers may support a completed-live claim. Registry aliases
remain routing only and never imply Stable.

## Immutable recovery

Before any write, stop without registry change. After a successful write,
never overwrite or unpublish immutable bytes, reuse a defective version,
delete an observed `latest`, hide a partial state or advance an unverified
dependent. A package defect requires deprecation and/or a new reviewed SemVer.

Resume only after fresh observation at the last completed checkpoint. A
forward alias transition uses only the currently authorized pilot, base or core
command. A separately approved restoration to the fully observed M19 defaults
starts with the first alias that actually moved and proceeds core, base, pilot
only as required by observed state. Every command is independently approved
and verified; credentials, OTPs and recovery material never enter evidence.

| Last completed mutation | Truthful recovery boundary                                                                                         |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------ |
| None                    | Stop without registry change.                                                                                      |
| Core `next`             | Preserve core `0.4.0`; resume after fresh verification or use a new reviewed SemVer if defective.                  |
| Core/base `next`        | Preserve both `0.4.0`; keep defaults unchanged and do not claim coordinated completion.                            |
| All three `next`        | Preserve pilot `0.2.0`; reverify exact/`next` before any default move.                                             |
| Pilot `latest`          | Record the one-edge mixed window; separately advance base or restore pilot to its prior verified version.          |
| Base `latest`           | Record the one-edge mixed window; separately advance core or restore base, then pilot, to prior observed versions. |
| All defaults moved      | Do not close before complete exact/`next`/`latest`/unqualified evidence and a zero-finding final review.           |

The forward commands are, in the accepted order:
